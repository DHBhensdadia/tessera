# Tessera against ITC-2019

What Tessera's data model can hold of the International Timetabling Competition 2019
instances, and what it cannot.

Generated by `tessera fidelity` from the same code that performs the import, against the 36 instances pinned in [`scripts/itc-instances.sha256`](../../scripts/itc-instances.sha256). It is regenerated and compared in the test suite, so it describes the importer that exists rather than one that once did.

## The short version

**0 of the 36 instances import without loss.** None of them.

That is the honest headline and it is not a near miss. An ITC instance is mostly a *scheduling problem* — per-class time domains, ranked room lists, penalties on every alternative — and Tessera holds a *university*. What survives the crossing is the university part: rooms, courses, offerings, a teaching week, and when rooms are closed. What does not is the part a solver would consume.

The single reason for most of it is one sentence long. A Tessera session template must be taught to at least one student group; a cohort must name the structural groups it draws from; ITC states individual student enrolments and has no programme tree. So every class in every instance is dropped, and every distribution constraint with them — including the six types that **do** have a counterpart, because they would refer to classes that no longer exist.

Carrying them would mean inventing a programme tree the instances do not state, and then reporting a fidelity the invention created. That was ruled out before these numbers were known, which is the only time such a rule can be set honestly.

## The two sets are kept apart

**30 competition instances** (Early, Middle, Late) and **6 test instances**. Published results are comparable against the competition set; the test set is what the reference solvers are usually demonstrated on. Conflating them would make a benchmark claim that cannot be checked against the literature.

## Approximated

Held, but changed.

| | across all instances | |
|---|---:|---|
| room closures | 36 | widened to the coarser grid the instance had to be given; a closure rounded inward would free a room that is shut |

### The teaching grid

ITC states every time to **five minutes** across a 288-slot day. Tessera's `TimeGrid` allows at most 96 slots in a day, and that ceiling is not moved for a benchmark — a data model reshaped to fit a competition is optimised for the competition.

So each instance gets the finest grid that fits, over the hours it actually teaches rather than ITC's midnight-to-midnight day:

| slot length | instances |
|---|---:|
| 10 minutes | 25 |
| 15 minutes | 11 |

**0 instances keep five-minute resolution.** A single grid for all of them would have to be 15 minutes, so choosing per instance is what keeps 25 of them at 10.

### How well the grid would have held the class times

**1,059,604 of 2,078,981 class time options (50%) land on their instance's grid unchanged.**

This is a measurement, not a column in the tables above, and the distinction matters. Every class is dropped, so not one of these time options is in a project anywhere — counting them as *carried* would put a million things in the carried column that a reader could not find if they went looking. What the number says is narrower and still worth knowing: **if classes ever became representable, the teaching week is not what would stop them.**

Class times round **outward**, never inward. Rounding a 50-minute class down would hand the solver a room for the last five minutes of a class still in it, and the resulting timetable would be wrong while remaining perfectly consistent with the data it was given.

### Room closures are dropped rather than widened

ITC closes a room in named weeks; Tessera blocks a slot or does not. Widening a part-term closure to the whole term would block a room in weeks the instance says it is free — **not a lossy import but a wrong one**, and the kind of wrongness that produces a plausible timetable nobody can falsify. The mirror case is not counted as loss at all: a closure lying entirely outside the teaching day forbids nothing, because nothing can be scheduled there to forbid.

**The most-used constraint type in the whole benchmark has no counterpart in Tessera, and it appears in 36 of the 36 instances.** `SameAttendees` occurs 27,435 times.

`SameAttendees` means *these classes share students, so they must not collide and must allow time to travel between them*. In Tessera that is **implied** by student groups rather than stated as a constraint: two sessions taught to the same group cannot overlap, and nobody writes a rule to say so. Whether that is a genuine gap or a modelling difference is not something this report can settle — what it can do is refuse to hide the number.

Synthesising groups from it would make the figures above look considerably better and mean nothing, because the fidelity would be against structure this importer invented rather than structure the instance stated.

Every type is listed, including those with a counterpart. **They are dropped too**, and not because of the constraint: each one names classes, and no class is carried. A `SameRoom` over two classes that do not exist is not a constraint, and writing it as one would be this report flattering itself.

## What this says about Tessera

Three findings, in the order they are worth acting on.

**1. Partial-week teaching is normal.** 30 of the 36 instances have classes that run in some weeks and not others — AGH, Masaryk, Purdue, Bethlehem, Marymount. These are real universities, not a competition artefact. Tessera offers every week, odd weeks or even weeks; the instances carry arbitrary masks like *first half of term* and *one week only*. This is the strongest candidate for a genuine gap in the data model.

**2. A session must be taught to somebody.** Requiring a student group is, on its own, what drops every class in every instance. It is a sound rule for a university product — a lecture with no audience is a data-entry mistake — and an absolute barrier to a competition instance. Both are true at once, and the barrier is structural rather than a missing field: ITC has no programme tree to hang a group on, so there is nothing to map from.

**3. Per-class time and room domains have no home.** ITC gives every class an explicit ranked list of times and rooms with penalties; Tessera derives what is eligible from capacity, features and rules. That is a real difference in kind, not a missing field.

None of the three is fixed here. Reshaping the data model in the phase that discovered the mismatch would optimise it for a benchmark, and each of these is now a backlog entry naming the instances that prove it — which is more than the model had before this was measured.

## Reproducing this

```bash
tessera fidelity --instances /path/to/Instances --out docs/fidelity/itc-2019.md
```

The instances are not redistributed; registration at [itc2019.org](https://www.itc2019.org/) is required. Verify a download against `scripts/itc-instances.sha256` first — every number above is attached to those exact bytes.
